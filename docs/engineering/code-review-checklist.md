# Code Review Checklist

## 先看结论

好的 Code Review 不是挑格式，而是降低未来维护成本。优先看：正确性、可读性、边界条件、测试、可观测性和回滚能力。

---

## Review 顺序

1. **先看目标**：这个 PR 解决什么问题？是否有 issue / design / benchmark 背景？
2. **再看边界**：改动范围是否过大？是否混入无关重构？
3. **看正确性**：核心逻辑是否覆盖正常路径、异常路径和边界值？
4. **看可维护性**：命名、抽象、模块边界是否清楚？
5. **看测试**：新增/修改的行为是否有自动化测试？
6. **看运行风险**：配置、迁移、权限、性能、兼容性和回滚方案。

---

## Checklist

| 维度 | 检查问题 |
|------|----------|
| Correctness | 是否存在空值、边界值、重复提交、幂等问题？ |
| API / Contract | 输入输出、错误码、兼容性是否清楚？ |
| State | 是否修改数据库、缓存、队列、文件或外部状态？ |
| Performance | 是否引入 N+1、全表扫描、大对象拷贝或同步阻塞？ |
| Security | 是否处理权限、注入、敏感信息、越权访问？ |
| Observability | 是否有日志、指标、trace、错误上下文？ |
| Test | 是否有单测、集成测试、回归用例或手动验证记录？ |
| Rollback | 是否可以灰度、回滚、降级或 feature flag 控制？ |

---

## Review 输出建议

- `must fix`：合并前必须改；
- `should fix`：强烈建议改，可由作者判断；
- `nit`：风格或小建议，不阻塞；
- `question`：需要澄清设计意图；
- `follow-up`：不阻塞本次合并，但应创建后续任务。
